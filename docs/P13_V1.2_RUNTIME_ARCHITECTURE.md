# P13 · v1.2.0 Runtime Architecture Hardening（运行时架构加固设计）

> 本文档是 v1.2.0 的**设计先行文档**：先设计、后编码。所有阶段实现必须与本设计一致；
> 偏离必须在本文档记录修订。语义行为（SEMANTIC_MODEL v1.1 已确认部分）一律不变。

## 0. 背景与问题

v1.1.0 及之前的执行模型（EXECUTION_ENGINE §1）：

```
source → compile(异步, tree-sitter wasm) → Program → runProgram(同步)
       → RunResult { initialSnapshot, steps: ExecutionStep[](每步含完整 Snapshot), status, output }
       → React 主线程索引播放
```

两个核心问题：

1. **主线程阻塞**：`runProgram` 在 UI 主线程同步执行整个程序。最坏情形
   （step-limit 10000 步 + 大状态 + 墙钟 10s 上限）期间主线程完全冻结——
   按钮无响应、无法取消、无法显示进度。
2. **内存复杂度**：每个 `ExecutionStep` 持有完整 `Snapshot` 深拷贝，
   Trace 内存 ≈ `steps × 状态规模`。500 单元 × 10000 步的规模下达到数十 MB 至
   数百 MB（实测见 `docs/runtime-baseline.json`）。

## 1. 目标与非目标

### 目标

- Interpreter 执行移出主线程（Web Worker），主线程不再被长程序冻结
- 支持运行中取消（尽快终止，不能只在 UI 忽略结果而 Worker 继续烧 CPU）
- 流式批量步骤：边执行边接收，UI 显示"已生成 N 步"
- TraceStore + Checkpoint/Delta：持久 Trace 内存显著下降
- 任意步骤快照可确定性恢复；Previous/Next/Restart/Timeline/随机跳转行为不变
- runId 防竞态：旧 Run 的消息不得污染新 Run
- 语义结果与 v1.1 完全一致（Full Snapshot 等价性金标验收）

### 非目标（本轮禁止）

- struct / malloc / scanf / 二维数组 / 字符串数组 / CFG / 表达式树 / 深色模式 / i18n
- 重设计整体 UI（仅新增 Running/停止/进度显示）
- 改变任何 v1.1 已确认的 C 语义、maxSteps=10000 保护、time-limit 教学语义
- 为了 O(1) Previous 引入双向 Patch（采用 Checkpoint + 前向重建）

## 2. 现状审计摘要（2026-09-23，main @ f379908）

| 项 | 现状 |
| --- | --- |
| 默认保护 | `maxSteps=10000`、`timeLimitMs=10000`、`maxCallDepth=100`（interpreter/index.ts） |
| 快照结构 | `Snapshot { scopes, cells, callStack, nextAddress, output }`，纯可序列化 |
| 状态变更路径 | cells 只新增/覆写（allocCell/writeCell/declareScalar 重声明复位），**从不删除**；scopes 仅尾部 push/pop；scope.vars 仅追加（对象创建后不可变）；callStack 仅尾部 push/pop；output 仅 `+=` 追加（builtin.ts）；nextAddress 仅递增 |
| 播放依赖 | UI 只读 `steps[i].snapshot`、`step.changed/flowEvents/description/status/line/evalTrace`；Previous/Next/Timeline 全部是索引运算，**不重演执行** |
| 竞态现状 | App 有 `runSeq` ref 防过期结果，但运行期间 UI 冻结，无从编辑/取消 |
| WASM 加载 | 主线程 `installWebCstLoader()`（`?url` 导入两个 wasm，Vite 打包为 assets，Pages base 生效）；Node 测试走 `require.resolve` |
| 构建产物 | v1.1 main JS ≈ 954 KB（含 web-tree-sitter + 解释器 + CodeMirror + React） |
| 测试基线 | 441 通过 / 27 跳过（本地无 gcc 的 GCC 差分用例，CI 全跑）/ CI Node 22/24 绿 / Pages 绿 |
| 版本一致性 | `release.test.ts` 断言 package.json 版本 = CHANGELOG 最新版本 = 1.1.0 |

**关键结论（决定 Delta 设计）**：快照的全部可变状态就是五个字段，且作用域/栈/输出
均满足"尾部操作/追加"结构 → **相邻快照 diff 生成的 Delta 天然构造性完整**，
配合防御性 `snap-set` 兜底操作，正确性不依赖任何"解释器恰好没写某处"的假设。

## 3. 总体架构

```
┌─ Main Thread ──────────────────────────────────────────────┐
│ App.tsx（编辑 / 播放状态机）                                  │
│   ↕ RuntimeClient（src/worker/client.ts：runId 过滤/取消/恢复）│
│   ↕ TraceStore（src/core/trace/：checkpoint+delta 存储与重建）│
└──────────────┬─────────────────────────────────────────────┘
               │ 结构化克隆 postMessage（typed protocol）
┌──────────────▼─────────────────────────────────────────────┐
│ Web Worker（src/worker/runtime.worker.ts）                   │
│   tree-sitter wasm 初始化 → compile → Interpreter.runProgram │
│   TraceAssembler（边执行边产出 record+delta/checkpoint 批次）  │
└─────────────────────────────────────────────────────────────┘
               ↓ Streaming Execution Events（STEP_BATCH…）
```

- **主线程保留**：源码编辑、运行请求、步骤接收、播放/时间轴、全部面板渲染。
- **Worker 承接**：parser(wasm) 初始化、compile、Interpreter、trace 组装。
- 主线程代码图不再引用 `core/cst` / `web-tree-sitter` / 解释器重路径 →
  实现 bundle 拆分（§14）。

## 4. Worker 边界（设计点 1）

- 单一 Worker 实例，惰性创建（首次 Run 时），跨 Run 复用；生命周期归 `RuntimeClient`。
- Worker 为 `type: 'module'`（Vite `new Worker(new URL('./runtime.worker.ts', import.meta.url), { type: 'module' })`），
  Vite 自动独立打包 worker chunk，Pages base 对 worker 内资源同样生效。
- Worker 内部安装自己的 wasm 加载器（复用 `ui/cst-web` 的 `?url` 导入方式）；
  `Parser.init` / `Language.load` 只依赖 fetch + WebAssembly，Worker 环境均可用。
- **不塞进 Worker 的东西**：React 状态、播放逻辑、面板渲染——它们本来不耗时，
  强行 Worker 化只会增加消息复杂度（P13 原则：不为形式而架构）。

## 5. Worker Protocol（设计点 2）

类型定义集中在 `src/worker/protocol.ts`（discriminated union，主/Worker 共享，
不含任何重依赖）。**所有消息一律携带 `runId`**（`WORKER_ERROR` 允许 null）。

Main → Worker：

| type | 字段 | 语义 |
| --- | --- | --- |
| `COMPILE_RUN` | `runId, source, options?{maxSteps,timeLimitMs,maxCallDepth,batchSize}` | 编译并执行；函数参数不可跨线程，batch/取消由 Worker 内部装配 |
| `CANCEL` | `runId` | 优雅取消请求：Worker 空闲（编译前/已结束）时回 `CANCELLED`；解释器同步执行中无法处理消息，由主线程 terminate 硬取消（§7） |
| `DISPOSE` | — | 释放 Worker（应用卸载） |

Worker → Main：

| type | 字段 | 语义 |
| --- | --- | --- |
| `READY` | — | Worker 就绪（wasm 初始化完成） |
| `RUN_STARTED` | `runId, initialSnapshot` | 编译成功、开始执行；initialSnapshot 是锚点 -1 |
| `STEP_BATCH` | `runId, startIndex, entries: TraceEntry[]` | 批量步骤（§8）；`TraceEntry = { record: StepRecord, state: TraceEntryState }`，`state = { format:'full', snapshot } \| { format:'delta', delta }` |
| `RUN_FINISHED` | `runId, status, output, totalSteps` | 终态：`completed \| runtime-error \| step-limit \| time-limit \| cancelled \| empty` |
| `COMPILE_ERROR` | `runId, errors: CompileError[]` | 编译失败（终态之一，不产生步骤） |
| `CANCELLED` | `runId` | Worker 侧优雅取消完成 |
| `WORKER_ERROR` | `runId?, message` | Worker 意外异常/初始化失败（终态） |

与任务书示例清单的差异说明：`RUN_PROGRESS` 并入 `STEP_BATCH`
（`startIndex + entries.length` 即进度，独立消息是冗余）；`RUNTIME_ERROR` 并入
`RUN_FINISHED.status`（运行错误本就是 trace 内的终止步骤 + RunResult.status，
v1.1 语义不变）；新增 `CANCELLED` 与 `COMPILE_ERROR` 显式化两条终态路径。

**StepRecord**（§"ExecutionStep 与状态分离"）：

```ts
type StepRecord = Omit<ExecutionStep, 'snapshot'>;
// { id, line, endLine, statementType, phase?, changed, evalTrace?, flowEvents, description, status, errorCode?, outputDelta? }
```

`ExecutionStep` 类型保留为**视图类型**（record + 重建快照的装配结果），
现有语义测试与 UI 心智模型不变。

## 6. Execution Lifecycle（设计点 3）

```
idle → (COMPILE_RUN runId=N) → compiling → RUN_STARTED → running
     → STEP_BATCH ×k → RUN_FINISHED(status) → idle
任一终态（含 COMPILE_ERROR / WORKER_ERROR / CANCELLED）后 Worker 回到 idle。
Client 状态机同步迁移：idle → starting → running(累计进度) → finished/cancelled/error。
```

- 编译错误：`COMPILE_ERROR`，旧 runResult 与 sourceDirty 语义维持 v1.0.2 规则。
- 空程序 / 缺 main：编译期已拦截（E_NO_MAIN），同样走 `COMPILE_ERROR`。

## 7. Streaming 策略（设计点 4）+ Cancel（设计点 5）

### 7.1 流式批量

- `RunOptions` 新增**观测性**回调 `onStep?(step: ExecutionStep, prevState: Snapshot | null)`：
  `finishStep` 每生成一步即调用一次；`prevState` 为上一步之后的快照（首步为
  `initialSnapshot`）。该回调纯观测——解释器不读取其任何副作用，**不影响确定性**。
- Worker 侧 `TraceAssembler`（纯模块，Node 可单测）：维护 prevState 与批缓冲，
  每步产出 `TraceEntry`（Phase B/C 全为 `full`；Phase F 起按 Checkpoint 间隔切
  `full`/`delta`），攒满 `batchSize`（默认 100，benchmark 校准）即
  `postMessage(STEP_BATCH)`；`RUN_FINISHED` 前冲刷残余批次。
- **postMessage 不让出 Worker 事件循环**——批次在解释器继续执行的同时异步送达
  主线程，这正是"执行中显示已生成 N 步"的实现基础。
- **禁止每步一条 postMessage**（任务书 §9）：batch 100 倍降低消息与克隆开销。

### 7.2 取消（关键决策）

解释器是同步递归下降，**运行中的 Worker 无法处理任何入站消息**
（消息只能在其事件循环空闲时被分发）。因此：

- **硬取消 = 主线程 `worker.terminate()`**：立即杀死执行（不烧 CPU），
  客户端本地合成"已取消"终态并丢弃该 run 的部分批次（runId 隔离保证不污染）。
  Worker 标记为 dead，下次 Run 惰性重建（wasm 重初始化成本实测记录于 benchmark）。
- 解释器同时提供 `shouldCancel?: () => boolean` 检查点（`finishStep` 每步检查，
  命中抛 `CancelSignal` → 追加 `status:'cancelled'` 终止步骤，`RunResult.status`
  新增 `'cancelled'`）。它服务于：单元测试驱动取消路径、进程内嵌入场景、
  以及未来异步化改造；对远程 CANCEL 不承担语义（诚实记录，不假装能收消息）。
- `CANCEL` 消息：Worker 空闲时回 `CANCELLED`；忙时主线程不等它，直接 terminate。
  UI 上"■ 停止"按下后至多一次事件循环轮转即生效，无 10s 尾巴。

### 7.3 状态区分（任务书 §26）

`RunResult.status` / `RUN_FINISHED.status`：`completed | runtime-error | step-limit |
time-limit | cancelled | empty`；客户端另有 `worker-error`（Worker 故障，非程序语义）。
**cancelled ≠ step-limit**：step-limit 是教学保护步骤（保留完整说明文案），
取消是用户主动行为，两者状态、文案、测试全部分离。

## 8. Checkpoint 策略（设计点 6）与 Delta 格式（设计点 7）

- **Checkpoint 间隔 K = 100 步**（初值；以 Phase A/H benchmark 校准：
  权衡重建成本 O(K) 与锚点密度）。入口 `initialSnapshot` 即锚点 -1。
- 批大小 batchSize 与 K 解耦（batch 是传输参数，K 是存储参数）。
- **Delta = 相邻快照 diff**（Worker 侧对 `prevState → step.snapshot` 计算），
  构造性完整：diff 遍历快照全部五个字段，任何结构异常回退 `snap-set` 整体兜底。

```ts
type SnapshotDelta =
  | { op: 'cell-set'; addr: number; cell: MemoryCell }     // 新增或整体覆写
  | { op: 'cell-del'; addr: number }                        // 防御（当前引擎不会删单元）
  | { op: 'scope-push'; scope: Scope }                      // 尾部压入（含已有 vars）
  | { op: 'scope-pop' }
  | { op: 'var-add'; scopeId: number; variable: Variable }
  | { op: 'var-update'; scopeId: number; name: string; variable: Variable } // 防御
  | { op: 'frame-push'; frame: StackFrame }
  | { op: 'frame-pop' }
  | { op: 'frame-set'; frames: StackFrame[] }               // 防御：非纯尾部变化
  | { op: 'output-append'; text: string }
  | { op: 'output-set'; text: string }                      // 防御：非追加变化
  | { op: 'next-address'; value: number }
  | { op: 'snap-set'; snapshot: Snapshot };                 // 终极兜底：整体替换
```

diff 规则（确定性，键序固定）：cells 按 addr 升序；scopes/frames 按
"最长公共前缀 + 尾部操作"判定，出现中间插入/删除/字段漂移立即回退 `snap-set`；
output 必须是前缀关系否则 `output-set`；nextAddress 变化即记录。
**只存 after（前向 delta）**——Previous 由"最近重建缓存 + 前向重建"承担，
不引入双向 Patch（任务书 §16 采纳斯派）。

## 9. Snapshot 重建（设计点 8）与随机跳转（设计点 9）

```
getSnapshot(i):
  anchor = ≤ i 的最近 checkpoint（state 下标 -1 或 ≡K-1 的 full 条目；有序数组二分）
  snap = deepClone(checkpoint.snapshot)          // 绝不修改锚点本身
  for d in anchor+1 .. i: applyDelta(snap, entry[d].delta)
  return snap
```

- 重建是纯函数：同输入必同输出；锚点冻结不可变（克隆后操作）。
- **LRU 缓存 32 个重建结果**（播放连续 Next/Previous 命中近邻）；
  `clear()` 清空；追加批次不失效（已追加下标不可变）。缓存只是纯函数记忆化，
  不得影响结果（测试断言缓存命中与否内容逐字段一致）。
- 随机跳转 = `getSnapshot(i)` + `getStepView(i)`，O(clone(状态) + K×delta)。
  0 → 8000 → 120 → 9500 的拖动序列全部命中此路径；验收测试
  随机生成 1000 个 seek 与 Full Snapshot Oracle 逐字段 deepEqual（§15）。
- `getSnapshot` 返回**共享只读实例**（缓存契约，TRACE_STORE.md 记载；
  需要独立副本用 `getSnapshotCopy`）。UI 面板已核实全部只读。

## 10. 故障恢复（设计点 10）

| 故障 | 检测 | 恢复 |
| --- | --- | --- |
| Worker 构造失败 | `new Worker` 抛异常 | 客户端置 `worker-error`，UI 明确报错，Run 按钮恢复可用 |
| wasm 初始化失败 | READY 超时看门狗（5s）/ `WORKER_ERROR` | 同上；UI 横幅提示，绝不永久 busy |
| Worker 运行中 crash | `onerror` / `onmessageerror` | 置 `worker-error`，busy 解除；下次 Run 重建 Worker |
| 意外异常（compile/run 内部） | Worker try/catch → `WORKER_ERROR{runId}` | 该 run 终态，UI 报错 |
| 主线程消息含过期 runId | runId 过滤 | **静默丢弃**（防旧任务污染新任务） |

**不变式：任何路径下 UI 不得停在"加载中"**。每个 run 从发起时刻起必然到达
终态（完成/错误/取消），异常路径由上述机制闭合。runProgram 本身"绝不抛异常"
（v1.1 契约）继续成立；Worker 内部再包一层 try/catch 兜底。

## 11. 内存预算（设计点 11）

模型：全量 Trace ≈ `N × S`（N 步 × 状态规模 S）；Checkpoint+Delta ≈
`(N/K) × S + N × Δ`，Δ 为单步 delta（多数步仅几个 cell-set）。
以 500 cells × 10000 步、K=100 估：全量 ≈ 10000S；新方案 ≈ 100S + 10000Δ，
Δ ≪ S 时降幅接近 K 倍量级。**具体数字一律以 `docs/runtime-baseline.json`
（Phase A）与 `docs/runtime-v1.2-benchmark.json`（Phase H）实测为准**，
不预设虚假百分比。Worker 峰值内存（解释器 steps 数组仍为全量）与 v1.1 相同，
运行结束即释放；UI 持久内存为下降目标。若实测降幅不明显，在最终报告分析原因
（预期主要风险：evalTrace/flowEvents 等元数据占比高——它们不受本方案影响）。

## 12. Backpressure（设计点 12）

v1.2 采用**无确认推送**：生产者单一（一个 Worker）、批次有界（100 步/批，
含 500-cell 状态时约数百 KB 结构化克隆）、消费者（append + 节流渲染）远快于
生产者（解释器每步本身就要克隆快照）。播放期间 UI 渲染按 rAF 节流，
进度文本每批至多更新一次。**边执行边播放不属本轮目标**（任务书 §23 采纳斯派）：
运行中只累计与显示进度，RUN_FINISHED 后开放播放——消除"播放中途 trace 变长"
的状态复杂度。若未来实测出现主线程消费瓶颈，预留 `STEP_BATCH_ACK` 扩展位
（协议版本字段），本轮不实现。

## 13. 确定性（设计点 13）

- 解释器执行路径**零改动**（唯一新增是观测回调与 shouldCancel 检查，
  均不影响执行状态机）；同程序两次运行步骤序列逐位相同的既有断言继续成立。
- diff/applyDelta 为纯确定性算法（固定键序、无随机、无时间依赖）。
- 重建结果与全量快照逐字段 deepEqual（金标测试，§15）——不一致时**默认新架构有 Bug**。
- LRU 缓存、批次切分、批大小均不得影响任何可见结果（由等价性测试覆盖）。

## 14. Pages 兼容与 Bundle（设计点 14）

- Worker 以 Vite 原生 `?worker`/`new URL` 方式打包，产物落 `assets/`，
  Pages base `/C-Visualizer/` 自动应用于 worker chunk 及其内联的 wasm URL。
- `release.test.ts` 既有断言（wasm 资源齐全 + JS 内引用带 base）继续有效，
  **新增**：pages 产物含 worker chunk；worker JS 内 wasm 引用带 base；
  主 chunk 不再包含 tree-sitter 引导代码（bundle 拆分验证）。
- 记录 before/after：main chunk / worker chunk / wasm 尺寸；
  确认 tree-sitter 未双份打包进 main+worker（主线程不再 import）。
- 生产 build + Pages 线上 smoke（部署后真实浏览器验证）为发布门槛。

## 15. 测试策略（设计点 15）

| 套件 | 内容 | 手段 |
| --- | --- | --- |
| Interpreter 观测钩子 | onStep 序列/prevState 正确；shouldCancel 驱动 `cancelled` 终态 | Node 单测（无真实 Worker） |
| TraceAssembler | full/delta 两种格式的批切分、残余冲刷、checkpoint 间隔 | Node 单测 |
| Protocol / Client | 消息往返、runId 过滤、乱序/过期消息丢弃、COMPILE/RUNTIME/WORKER 错误路径 | **Fake Worker**（内存 MessageChannel 语义），协议 15+ 用例 |
| Race / runId | 连续 Run A→B、运行中编辑源码自动取消、快速三连 Run | Fake Worker 10+ 用例 |
