# v1.2.0 最终报告 — Runtime Architecture Hardening

> 日期：2026-09-23　|　tag：`v1.2.0`　|　基线：v1.1.0（main `f379908`）　|
> 仓库：https://github.com/yangxijia111/C-Visualizer　|
> 设计文档：[P13_V1.2_RUNTIME_ARCHITECTURE.md](P13_V1.2_RUNTIME_ARCHITECTURE.md)

本轮唯一主题：**执行架构重构**。不新增任何 C 语法；v1.1 已确认的语义行为
（SEMANTIC_MODEL）全部保留，并以金标等价验收逐字对拍。

## 【Architecture Before】

```
Main Thread（全部在 UI 线程）:
source → compile(tree-sitter wasm) → runProgram(同步执行整个程序, 最长 10s)
       → RunResult { steps: ExecutionStep[]（每步含完整 Snapshot 深拷贝） }
       → React 索引播放
```

问题 1：复杂程序运行期间主线程完全冻结（无法点击 / 无法取消 / 无进度）。
问题 2：trace 内存 ≈ steps × 状态规模（10k 步 × 500 单元实测保留 288 MB）。

## 【Architecture After】

```
Main Thread: 编辑 / 播放 / 面板渲染（双 TraceStore: building → display）
      ↕ RuntimeClient（runId 防竞态 / READY 看门狗 / 取消 / 故障恢复）
Web Worker: tree-sitter wasm → compile → Interpreter → TraceAssembler
      ↘ STEP_BATCH 流式批量（100 步/批，postMessage 不阻塞解释器）
Main Thread: TraceStore（Checkpoint 每 100 步 + 逐步 Delta + LRU 重建）
```

阶段推进（每阶段独立可回滚 commit，测试全绿后进入下一阶段）：
设计(P13) → A 基线 → B Worker 化+流式协议 → D 取消 → E TraceStore →
F Checkpoint/Delta → G UI 迁移 → H Stress/Benchmark → 发布。

## 【Worker Protocol】

见 [WORKER_PROTOCOL.md](WORKER_PROTOCOL.md)。要点：discriminated union 全消息带
`runId`（过期消息静默丢弃）；`RUN_STARTED` 先行携带锚点快照；批次 `startIndex`
严格连续；`RUN_FINISHED` 携带终态（`completed | runtime-error | step-limit |
time-limit | cancelled | empty`）；`WORKER_ERROR{runId:null}` 表示 Worker 级故障。
READY 看门狗 15s；任何故障路径都保证 UI 得到终态、不停在「加载中」。

## 【Cancellation】

同步解释器在执行中无法处理消息，因此远程取消 = 主线程 `worker.terminate()`
**硬取消**：立即终止（不烧 CPU）、本地合成 `cancelled` 终态、丢弃部分批次、
下次 Run 惰性重建 Worker。解释器同时提供 `shouldCancel` 每步协作检查点
（服务于测试与进程内嵌入；诚实记录其不承担远程取消语义）。
`cancelled` 与 `step-limit` 教学保护严格区分。UI：「■ 停止」按钮 + 编辑源码/
切换示例自动终止。实测停止后一次事件循环内恢复可运行状态。

## 【Trace Storage】

- 锚点：`initialSnapshot`（状态 -1）+ 每 K=100 步一个完整快照（K=1 等价全量）
- 其余每步：`SnapshotDelta[]`（相邻快照 diff：cells 升序 / scopes、frames 位置对齐 /
  output 前缀 / nextAddress；**构造性完整**，结构异常回退 `snap-set` 整体兜底）
- 重建：最近锚点二分 → 深拷贝 → 前向 apply；LRU=32 纯记忆化缓存（不影响结果）
- 只存 after（前向重建），不引入双向 Patch；Previous/随机跳转由重建承担

## 【Correctness】

金标等价（核心验收，tests/trace/golden-equivalence.test.ts）：
同一程序的**全量快照 trace vs Checkpoint+Delta store 重建**逐步 deepEqual——

- 21 个内置示例全部通过
- 14 个边缘语料：goto 后向前向、递归 fib、指针交换、switch 穿透、数组初始化列表、
  除零 / 未初始化读取 / 数组越界、深度超限、step-limit、printf/do-while、
  嵌套循环 break/continue、带副作用短路
- checkpoint K ∈ {1, 2, 97, 100000} 扫描全部等价
- 每程序 1000 次固定种子随机 seek 全部一致；LRU 热缓存与冷重建内容一致
- Delta property 测试（固定种子）：随机状态链与随机对 diff→apply 往返相等
- v1.1 既有语义测试（441 项）与 GCC 差分语料**一个未删、全部保留**

## 【Performance】

同机同方法对比（Node 24，强制 gc 保留堆；`npm run bench` 可复现）：

| 程序 | v1.1 生成 | v1.2 生成+装配 | 说明 |
| --- | --- | --- | --- |
| small (95 步) | 1.9 ms | 4.1 ms | 小程序噪声级 |
| medium 100 单元 (1562 步) | 44 ms | 112 ms | diff 为每步 O(状态) 追加成本 |
| fib12 (1863 步) | 145 ms | 255 ms | 同上 |
| goto (1003 步) | 10 ms | 13 ms | — |
| **large 500 单元 (10001 步)** | 1381 ms | 2559 ms | 生成耗时 ≈ 1.9×，但发生在 **Worker**，不再阻塞主线程 |

解释器单步执行本身无退化（diff 是解释器之外的装配开销）。示例级程序（几十步）
完全无感。

## 【Known Limitations】

1. 硬取消后下次 Run 需重建 Worker（wasm 重初始化约百毫秒级）；根因是同步解释器
   无法在执行中处理消息——分块执行可消除，留给 v1.3
2. 流式期间不可播放部分 trace（仅显示进度）；「边生成边播放」留待 v1.3
3. 小状态程序的 trace 内存无明显下降（元数据 evalTrace/flowEvents 占比高）——
   如实记录，未做虚假优化
4. 解释器侧运行期峰值仍持全量 steps（Worker 内、运行结束即释放）；
   Worker 内 streaming 截断留待后续
5. cancel 期间已排队的迟到批次依赖 runId 过滤兜底（已在协议层保证正确性）
